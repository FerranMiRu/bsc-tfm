\item Why they conflict: many small objects stress the metadata server.
\item Claim: general to any chunked format, not specific to this dataset.

Historically, Earth observation and climatological data have been distributed in GRIB or NetCDF formats \citep{Gowan2022, Kuluke2021}. However, both present structural limitations when integrated into modern machine learning pipelines. GRIB files read data sequentially, which is inefficient for repeated selective access. This design limits parallel I/O and lazy loading for efficient workflows. Additionally, its metadata must be fully parsed before extracting the data, making the format rigid and not efficient \citep{Gowan2022, Glahn2003}. NetCDF format relies on HDF5 and uses a chunk layout that is fixed at file creation. Its file handles are tied to individual processes, which causes I/O issues when multiple workers access the same dataset. The format also lacks native zero-copy tensor export, meaning data must pass through CPU RAM first, which doubles memory usage and slows training \citep{Huang2023, Russell2006}.

To overcome these limitations, we use Zarr, which natively supports chunked arrays, flexible metadata, and direct memory sharing for AI workflows \citep{Gowan2022}

\section{The dataset substrate: a harmonised 1850--2100 land-use cube}
The dataset we consider in this paper is created from seven separate sources, covering the years 1850 to 2100, and in a 1 km grid. Next, we will detail the processing performed to unify the data from these heterogeneous sources. This is also explained in \textit{citation to ML Earth paper?}

\subsection{Source datasets and provenance}

\textbf{Target Labels:} As a target, we use HILDA+ v1.8 \citep{winkler2020hilda+}, distributed via PANGAEA. This contains global land-use at 1 km resolution for the whole world, for the time period 1960--2020. It also expands back to 1899 using Random Forests. It distinguishes 13 classes, although we narrowed it down to 8 by combining all of the different forest sub-types into a single class. This is done since our predictors do not have enough information to distinguish between these different phenologies.
Version note: the pipeline uses HILDA+ v1.0; v2.0 (2025) was released after the pipeline was finalised, and versions are kept consistent with \citet{mozaffari2026scalable}.

\textbf{Predictor Variables:}
\begin{itemize}
    \item \textbf{LUH2} (historical v2h and future v2f) \citep{hurtt2020harmonization}, obtained through input4MIPs/ESGF. This is a global land-use dataset at $0.25^{\circ} \times 0.25^{\circ}$ ($\sim$31~km) resolution, covering the years 1850--2015. We employ the 12 fractional land-use state variables and two secondary-vegetation parameters (mean age and biomass).
    \item \textbf{Köppen-Geiger} climate classification maps \citep{beck2018present, beck2023high} from GLoH2O
    \item \textbf{ISIMIP2b} population data from the ISIMIP HistSoc protocol \citep{frieler2017assessing}
    \item \textbf{GEBCO 2024} elevation and bathymetry \citep{GEBCO2024}
    \item \textbf{PNNL} \citep{li2024global} high-resolution global derived slope and aspect, and soil (texture, organic carbon)
\end{itemize}


\subsection{Spatiotemporal coverage and grid}
To remain consistent across datasets, the input data was aligned to the 1~km WGS84 grid from the HILDA+ dataset.

\textbf{Köppen-Geiger:} Since climatic zones are only available at 30-year intervals, we needed to perform a yearly interpolation that returned valid classes in between the data available. We achieved this by using \textit{stochastic weighted dithering}. For each pixel, we consider the class it has at available time points $t$ and $t+30$. To interpolate for the years in between, we take the starting class and only switch to the ending class if a noise value is lower than a time weight $w(t)$. This weight is assigned so that the probability of switching classes grows linearly across the 30-year interval. We also consider that the pixel will transition a single time in that whole period.

\textbf{ISIMIP2b:} Population data is at $0.5^{\circ} \times 0.5^{\circ}$ resolution and starts at the year 1861. For the spatial issue, we interpolated using population density. Population counts are converted to density ($people/m^2$), conservatively remapped to the target grid, and multiplied by the target cell areas to recover local counts. In terms of the temporal missing data, we used linear back-casting to get data starting on 1850, using the trends from the initial decade (1861–1871) and enforcing a lower limit of zero.

\textbf{PNNL soil data:} In the original dataset there is six-layer vertical soil data. To simplify it, we computed a 2D non-linear depth-weighted average with a decreasing weighting scheme of $w = [0.40, 0.25, 0.15, 0.10, 0.05, 0.05]$.

\section{Two representations of one dataset}

In this section we describe the two on-disk built from the same data cube. The interoperable store, which focus on discoverability, accesibility and self-description by preserving all the metadata required for a data reconstruction; and the training-optimised merged store, which has been designed to be more effective in the training process by dropping the non-essential metadata and applying a more efficient layout in terms of I/O. Therefore, both formats store the same data, they are different objects that differ in layout, and metadata strategy, which is the baseline for the trade-off analysis.

\subsection{The interoperable (FAIR) store}

Focusing on the interoperable store, each variable is stored in a different Zarr array. Applying this layout we can preserve data semantic identity and their processing history preserved directly within the variable attributes. This metadata strategy ensures that the data remain understandable and traceable, even without access to the original source or processing scripts. Thus, this design ensures reproducibility, as any consumer can verify how the data were obtained and processed. This layout schema also enables users to inspect and visualize the data easily, by using standard scientific libraries.

This store has been designed to accomplish the FAIR principles:
\begin{itemize}
    \item \textbf{Findable}: \textbf{it has been published as a DOI-registered artifact \cite{doi_ref} and indexed in the BSC AI Factory data catalog.}
    \item \textbf{Accessible}: We have used a layout that enables an easy visualization and manipulation via standard libraries (e.g., \textit{xarray}, \textit{numpy}...);
    \item \textbf{Interoperable}: through CF-compliant conventions attributes have been standardized;
    \item \textbf{Reusable}: By inspecting the metadata, every consumer can follow the processing history of the data and its origen, which provide complete context for validation.
\end{itemize}

\subsection{The training-optimised merged store}

After implementing the AI4Land model training pipeline with the interoperable store, we identified a significant I/O bottleneck that delayed data ingestion. The diagnosis and quantification of this limitation are detailed in Section 4. To address it, we designed a training-optimized layout structured as a single Zarr store containing two coordinate-defined groups: static (non-temporal variables) and dynamic (time-indexed variables). Each group holds exactly one consolidated Zarr array, collapsing all variables into a unified structure. Original variable names are promoted to an explicit coordinate dimension, adding one axis while preserving the original spatial and temporal coordinates. Per-variable descriptors are stripped during this consolidation, as they are redundant for training workflows. This layout prioritizes ingestion throughput over data discoverability, significantly reducing initialization overhead and accelerating batch loading.
\subsection{What each representation gives up}

To sum up, each format presents a clear trade-off, trading one advantage for another. The interoperable store sacrifices raw I/O throughput to maintain rich, per-variable semantics and a self-describing structure. The training-optimized merged store, in contrast, trades semantic depth and general-purpose usability for speed, collapsing variables into unified groups and dropping non-essential metadata. This consolidation also trades storage efficiency for ingestion performance. The consequences of these design choices are detailed and quantified in Sections 4 and 6.
